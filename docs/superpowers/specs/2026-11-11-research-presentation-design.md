# Research, source reliability and presentation completion

The owner requested completion of the remaining dashboard work, including research questions, presentation and data sources, after the first verified local/LAN release. Existing scientific contracts and the approved Linux/Docker Compose/LAN deployment remain binding. This is a continuation of that authorized implementation.

## Approach

Extend the existing React/FastAPI/SQLite application. A replacement framework would discard working evidence/recovery paths; a cosmetic reskin would leave real collection and interpretation defects. The selected implementation improves the research answers, source reliability and working surface together. A concise dashboard is the implementation default; an optional preference question was sent, and a later answer can steer presentation without blocking independent research fixes.

## Research and evidence

Every one of the 37 questions must expose a short, server-computed, dated finding when its accepted inputs support one. Missing/withheld values produce an explicit explanation, never a synthetic answer. Summaries must use each observation's own date, denominator, unit and population; they cannot describe correlation as causation or a descriptive historical comparison as a forecast.

Correct G03's market-cap/P-E estimate to an implied index earnings proxy: MSCI normalized earnings, inclusion factors and unmatched P/E denominator coverage do not establish worldwide realized consolidated net income. Keep the original-method deferral, and make verified alternatives understandable. Refresh stale research descriptions from the actual archived evidence without weakening acceptance gates. Personal portfolio examples remain labelled examples until the owner supplies their inputs.

Expose a read-only research-status API derived from the existing acceptance snapshot, contracts and limitation register. It reports all questions, role dispositions, limitations and current assessment counts. It is not another acceptance engine and never authorizes data the canonical engine withholds.

## Source reliability

Fix OECD annual window rounding at the adapter boundary; the ingestion service must continue refusing out-of-window values. Reuse a common publisher response within a collection router/batch only while preserving original response evidence and independent per-series receipts. A subsequent collection must be able to fetch revisions. Investigate/fix bounded multi-document starvation, particularly WID, without increasing publisher budgets or accepting partial originals.

Separate observation freshness from the last collection outcome. A deferred refresh can coexist with current data; a successful request can still contain old data. Keep existing response fields compatible, show missing/stale/current evidence independently and identify the engine questions using each source. Acquisition uses the canonical managed client and durable ledger. No purchases, invented contact identity, access-denial retries or direct-network acknowledgement without verification.

## Presentation

Visual thesis: a restrained economic research workspace with clear typography, calm surfaces, one accent, and charts that carry the findings.

Content: overview with explicit loading/readiness and dated findings; searchable questions and research state; a focused topic/question workspace; saved independent figures; secondary methods/source/operations details. Avoid a marketing hero and a six-card mosaic leading to a page tens of thousands of pixels long.

Preserve every question and existing hash deep link. Make navigation and theme/data controls reachable at 390px. Add a page heading, main landmark and skip link. Preserve keyboard operation, chart tables, exact exports, saved-view conflict handling and original-source disclosures. Reflow or visibly scroll wide graphics with access to all labels; do not crop meaning. Respect reduced motion, including anchor scrolling. Keep calculations on the server. Use brief state/reveal transitions only where they improve navigation.

## Verification and delivery

Reproduce source/interpretation bugs before fixes and use independent numerical fixtures for summaries. Run the full offline Python/frontend suites, production build, browser flows and isolated container/recovery checks for the final code. Review real desktop/390px light/dark screenshots and all question navigation. Stage acquisition against a recoverable copy, audit the resulting corpus and report actual state changes. Retain the previous local/server images and matching data. Only replace the finance service after verification; preserve the original divergent server corpus and unrelated services.

No test certifies missing worldwide issuer coverage, actual personal inputs, formal owner visual approval or predictive validity. Those limits must be visible in the delivered application and release record.
